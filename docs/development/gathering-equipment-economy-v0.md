# 採取・装備制作・市場・整備 v0

2026-09-05 / Playground `play/gyai/gathering-equipment-economy`。
Creatorから保存形式変更と既存状態の移行を含む実装の承認済み。
本編への採用・mainへの統合は別のReview / Manual Smokeを要する。

## 今回の判断

「採取 → 精製 → 個別装備を制作 → 自分で使う／売る → 戦闘由来のオーブで仕上げる」までを実際に操作できる形にした。
市場があるだけで経済バランスが完成したとは扱わない。価格形成、所得速度、プレイヤー人口による検証はこれから。
既に評価された丸みのある日本語フォントと工房の配色・配置を維持し、装備庫・市場は装飾した標準チェストを使用する。

## 入手と制作

- `Exchange` による戦利品券→採取素材交換をサーバー側で拒否。画面だけ隠す対応ではない。
- 通常モブの戦利品は既存のオーブ・刻印粉・戦利品券を維持する。採取素材・精製材・完成装備の直接ドロップは追加しない。
- 素材は実際の採取か、採取したプレイヤーからの市場購入で供給される。
- 精製：同Tierの原料2個→加工材1個。既存仕様を維持。
- 武器制作：同Tierのインゴット4、板材2、加工石材1。
- 防具制作：同Tierのなめし革4、布2、加工石材1。
- T1〜T4を工房で選べる。ボスの討伐証は新品装備の制作に不要。
- 新品はノーマル、MODなし、強化0、整備度100。製作者UUIDと個体UUIDを保存する。
- 完成品は装備庫へ入る。現在の装備を勝手に上書きしない。
- 装備変更時は今の装備を装備庫へ戻し、MOD・強化値・レアリティ・整備度を各個体に保持する。
- 古いアカウントTier昇格アクションは互換処理として残るが、新工房からは使用しない。

## 市場

手帳の「市場」または港の「交易市場」→Tier選択→商品→価格確認→購入。

- 銀貨は独立した通貨残高。オーブとは別物。
- 戦利品券1枚→銀貨 `10 × Tier` 枚。高Tier地図の入手にも券を使用する旨を併記。
- 原料5種・加工材5種をTier別に出品できる。数量1〜999、1出品の合計価格を指定。
- 個別装備を出品できる。MOD加工・強化済み装備も同じ個体のまま移転する。
- 初期・移行装備は売却・納品・整備素材化できない。初期装備の換金ループを防ぐ。
- 素材は出品時にエスクローへ移し、装備は装備庫内でロックする。取り下げで返却／ロック解除。
- 購入は一括。売れた出品の再購入、価格不一致、自己購入、銀貨不足、保管上限、古い画面からの操作を拒否。
- 手数料5%切り上げを成約時だけ売上から引く。出品前に手数料と手取りを表示。
- オフライン出品者にも即時に売上を保存。受取ボタンを別途探させない。
- 銀貨上限10億、保管装備108個、出品24件。売り手側の銀貨上限も購入前に検証。
- 画面はスナップショット。「更新」または開き直しで再表示。確定処理は必ず最新の出品を再検証する。
- オーブ単品・欠片の出品、買い注文、検索文字列、価格履歴は今回未実装。

## 継続的な装備需要：整備

- 遠征を終了すると、装備中の武器・防具の整備度が各10減少する。正常な帰還・死亡帰還・中断後の終了を共通処理する。
- マップ生成失敗による返却 `AbortRun` では減らさない。
- 整備度0でも装備は消えず、遠征は可能。武器は加算攻撃補正-25ポイント、防具は最大HP-20。
- 同Tier・同種の新品（ノーマル、MODなし、強化0、整備度100）1個を部品として消費し、対象を100へ回復。
- 使用する予備装備を選択→確認→実行。対象装備の個体ID・製作者・MOD・強化値・失敗蓄積を維持。
- 装備庫上段の金床から整備へ。予備不足なら同Tier・同種の制作画面または市場へ進める。
- 整備度はTooltipにも表示。能力値の表示とサーバーの実ダメージ・最大HPは共通の補正を使う。
- 出品中、初期・引継ぎ装備、加工済み・使用済み装備を誤って部品にできない。

## ソロ検証用の港の納品

- 自作の新品だけ、全Tier・全装備共通で1日3個まで納品可能。完成品は消費される。
- 報酬は銀貨 `80 × Tier²`。更新はUTC日付、日本時間9時。
- 人口が少ない段階で制作→販売を検証する補助。無制限NPC買取をプレイヤー経済の代替としていない。
- 購入した装備の転売納品・初期装備の納品・加工済み装備の誤消費を防ぐ。
- 日付逆行では追加枠を与えない。回数は保存され、再接続でリセットされない。

## 保存・復旧

重要な実装：`CoreAccountService`（権威処理）、`CoreAccountRepository`（永続化）、`CoreEconomy`（個体・規則）。

- 専用core-loop保存のschemaを5へ更新。既存の別系統progression保存やprotocolは変更しない。
- v1〜v4を読む。既存の装備Tier、レアリティ、MOD値、強化値・失敗蓄積、熟練、素材、遠征、receiptを保持。
- 読み込みだけではアカウント本体を書き換えない。初回の書き込み前に旧形式の完全な `.vN.bak` を保存。
- 新規・旧データの装備に決定的な個体IDを割り当てる。旧装備の売却は不可、装備・MOD加工・整備は可能。
- 単一アカウント操作は既存のrevision＋receipt＋atomic rename方式を維持。
- 二者取引は同一保存ディレクトリの `market.lock` で直列化。双方の入力revisionを検証する。
- 買い手・売り手の完全な次状態（各checksum付き）を `market.pending` に原子的に記録してから双方へ設置する。
- 次の読み書きより先に未完了取引を復旧。片方だけ保存済みでも同じ結果へロールフォワードする。
- durable intent後の障害を「未消費」と偽って返さず、セッションの台帳キャッシュを無効化し再接続を案内する。
- 不整合なjournal、未知形式、checksum不一致を勝手に初期化・上書きしない。
- 稼働中の実プレイヤーデータへは、この実装作業中にアクセス・移行・初期化していない。

## 受け入れ検証

- T1〜T4の採取→精製→個別制作→装備→保存→再読み込み。
- v4のMOD・強化値保持とバックアップ。v1〜v3の既存移行テストも継続。
- 素材エスクローの取り下げ、装備の出品ロック、加工済み装備のオフライン売買。
- 二重購入、二人の同時購入、価格不一致、自己購入、資金・装備庫上限。
- 通常保存失敗時の未消費、二者保存途中の停止→再読み込み→一度だけ完了。
- 納品日次上限、整備による予備装備消費と対象個体の完全保持。
- 実メニューのpacked/unpackedクリック：選択だけで消費しない、数量・合計価格の確認、銀貨不足時の実行不可。
- 最終Test / Build結果はこの文書末尾に記録する。

## Debugの入口と留意事項

入手や数量の不一致は `CoreAccountService.apply/buy`、売買復旧は `CoreAccountRepository.recoverTrade`、表示・動線は `CoreLoopMenus` から確認する。
`market.pending` が残った場合は削除して取り繕わず、双方のrevisionとjournalを保全して調査する。
旧バイナリへ戻す際はv5を読めない。現行データと取引記録を保全し、バックアップへの復元は別途判断する。

価格・納品量・整備頻度はすべて今回の仮バランス。製造の基礎品質抽選、8部位化、重量別防具、細かな職人名表示、相場UIは未実装。
サーバー全体で一つの市場ファイルロックを使うPlayground版であり、大規模MMO向けDBや複数サーバー常時同期まで完成したものではない。
クライアントのコードは変更せず、サーバー処理と既存リソースパックだけを使用。起動・ゲーム操作・Manual Smokeは今回未実施。
