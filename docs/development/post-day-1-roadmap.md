# Day 1以降の開発順序

この文書は、Day 1 Combat基盤の後に何を作るかを固定する。

## 最重要方針

ProjectS v2では、機能を横に広げて大量に30%完成させるより、まず1つのクラスを端から端まできれいに完成させる。

目的は:

> 1クラスを完成させる → ProjectSで「クラスを1つ作る方法」を理解する → 必要なら2クラス目で共通化が正しいか確認する → その後に新クラス/MOD/Boss/装備等へ横展開する

とする。

先にGeneric Class Frameworkを作らない。実際の完成クラスから共通部分を抽出する。

## 前提 — Day 1 Combat基盤

Day 1の必須範囲は:
- 武器ごとの通常攻撃基盤
- Heavy Blade / 穿龍棍系
- Attack Speed比較
- 回避
- 固定攻撃テスター

弓は時間が余った場合の追加実験とし、必須ではない。

ここでは「装備中の武器に応じて左クリックの基本攻撃そのものが変わる」Combat基盤を成立させる。

## Phase 2 — 第一クラスを完成させる

まず1クラスだけを対象に、実際に遊べる完成形まで持っていく。

### 第一クラス完成に含めるもの

- 対応武器
  - 最低1武器から開始してよい
  - 最終的にはそのクラスの対応3武器まで確認する
- 武器ごとの通常攻撃
- Skill 1
- Skill 2
- Skill 3
- Ult
- 回避
- Mana
- Cooldown
- 固有ゲージは最初1つの使い道があればよい
- SkillのServer側判定/Damage
- 最低限の視覚エフェクト
- Sound / 命中Feedback
- Combat UI
- 重要箇所の自動Test
- 実際の敵/Boss相手に一通り遊べる状態

固有ゲージは最初から全ビルド分の使い道を作らない。まず1つ実装して遊び、必要になった時に追加する。

この段階の目的は:

> ProjectSで「1クラスを完成させる」とは何を作ることなのかを、実物として確立すること。

## Phase 3 — Combat UIまで含めて第一クラスを完成させる

UIは後付けの装飾ではなく、クラスのゲーム体験の一部として扱う。

最低限表示する候補:
- Skill 1〜3のCooldown
- Ult状態
- Mana
- 固有ゲージ
- 必要になった最小Buff/Debuff表示

高品質な最終UIを先に作る必要はないが、PlayerがCooldown/Mana/固有ゲージを見ながら判断できる状態まで持っていく。

第一クラスは「ロジックだけ完成」ではなく、実際にUIを見ながら遊べるところまでを完成扱いにする。

## Phase 4 — Boss 1体で第一クラスを実戦確認

Bossは第一クラス制作と並列で土台を作ってよい。

初期Bossは:
- HP
- 基本移動
- 攻撃3〜4個
- 明示的な攻撃予兆
- 特徴的な仕組み1個
- 必要ならPhase変化1回
- 死亡処理

程度に留める。

専用3Dモデルや本番Production Boss Frameworkは必須ではない。

第一クラスのSkill/UI完成後にBossの隙・攻撃間隔・HP等を調整し、通常攻撃/Skill/回避/Mana/固有ゲージを全部使って戦えることを確認する。

## Phase 5 — 必要なら第二クラスで設計を検証する

第一クラス完成後、すぐ3クラス全部へ横展開しない。

共通設計に不安がある場合だけ、性格の違う第二クラスを最小限作って確認する。

例:
- 1武器
- Skill 1または少数Skill
- 第一クラスとは異なるMana重要度
- 異なる固有ゲージ
- 同じCombat UI基盤

ここで確認すること:
- 何が全クラス共通なのか
- 何が第一クラス固有だったのか
- 武器側に置くべきものは何か
- クラス側に置くべきものは何か
- UIの共通部分はどこか
- データ化すべき部分はどこか

第一クラス用に作った構造へ第二クラスを無理やり押し込む必要が出るなら、その時点で設計を修正する。

問題なく作れるなら、第二クラスは確認用の最小実装で止めてもよい。

## Phase 6 — ここから横展開

第一クラスが完成し、必要なら第二クラスで設計確認まで終わった後は、その時点で最も価値の高い方向へ進む。

候補:
- 新しいクラスを完成させる
- MOD/装備Buildを作る
- Bossを追加する
- 装備/成長を広げる
- Mobを追加する
- Mob Editorを作る
- 最小Hunt/Quest loopを強化する

「ロードマップに書いてあるから次は必ずこれ」とはしない。完成した第一クラスを基準に、その時点で一番ゲーム価値が高いものを選ぶ。

## MODへ進む場合

Combat UIとBoss戦が成立した後、MOD/装備Buildへ進める。

初期候補:
- Attack Speed
- Skill Damage
- Mana回復
- Mana最大値
- Skill Cooldown
- 固有ゲージ獲得量
- 特定Skill強化

最初から大規模なMOD Poolを作らない。

同じBossを:
- 基準Build
- Attack Speed Build
- Mana Build
- Skill強化Build
- 固有ゲージBuild

などで再戦し、Build変更によって戦い方が明確に変わるかを見る。

## 最初の大きな成功地点

第一クラスについて:

- 通常攻撃
- 対応武器
- Skill 1〜3
- Ult
- 回避
- Mana
- Cooldown
- 固有ゲージ
- VFX/Sound/Hit feedback
- Combat UI
- Boss実戦

が一つの完成した体験として繋がっていること。

さらに同じ完成品を見れば、AIにも人間にも:

> 「ProjectSで次のクラスを作る時は、この完成品を基準にすればよい」

と分かる状態を作る。

これをv2最初の重要な成功地点とする。

## AI並列化候補

依存が切れた範囲で並列化する。

### Lane A — 第一クラスCombat
- Skill 1〜3
- Ult
- Mana
- 固有ゲージ最小版
- Cooldown

### Lane B — Boss
- Boss runtime
- 攻撃3〜4個
- 予兆
- Phase切替

### Lane C — Client Combat UI / Presentation
- Cooldown表示
- Mana表示
- Ult状態
- 固有ゲージ表示
- Skill VFX/Sound/Hit feedback

ただし各Laneを独立した完成品として肥大化させない。第一クラスを端から端まで完成させることが最終目的。

## やらないこと

第一クラス完成前に以下を先行しない。
- 3クラス全部
- 9武器全部
- 万能Class Framework
- 固有ゲージ万能システム
- 最終Mob Editor
- 本番Boss制作Pipeline
- 大規模MOD Pool
- 最終装備UI
- Market/Guild/Open World
- 汎用Framework先行開発

原則:

> 一つをきれいに作り切る。その完成品から次の作り方を学ぶ。
