# ProjectS — 戦闘・職業・ビルドの決定記録

> 基本の操作はオーソドックスで分かりやすくする。深さは、理解できる技能・武器・属性・パッシブの組み合わせに置く。βでは15キーストーンを含むツリーを、一通り遊べる完成した評価対象として出す。

記録日：2026年9月19日。対象は今回の戦闘・職業・武器・属性・スキルツリー・UIの設計会話。

関連文書：

## 0. この記録の読み方

**ここで合意したのは設計の方向と明示した範囲であり、実装済み・テスト済み・実機合格を意味しない。**

- 「決定」はCreatorが明示した要求、または直近の全体レビューへのOKで合意された方針を記録する。
- 方針だけ合意した項目では、個数・名称・係数・操作・実装方式まで確定したと解釈しない。
- 会話中にAssistantが例示した技能、ノード、数値、機能を自動的に採用しない。
- この記録だけを根拠に、既存技能・セーブ・クラスを削除したり、サーバーを更新したりしない。実装契約は未決事項を解決した対象範囲ごとに作る。
- 以前の文書やコードと異なる箇所は、今回の設計見直しとして扱う。古い仕様やWeb試作があることを、今回の未決事項が解決済みである根拠にしない。
- AION、Lost Ark、PoE、PoE2は参考にしたい体験を表す。過去の回答にあった他作品の仕様・個数の説明を、本書が検証・保証するものではない。

## 1. 今回決める範囲

基本職の入口、Warriorの再設計方針、技能数と複雑さの扱い、武器適性と越境の方向、戦い方と属性の組み合わせ、共通パッシブツリー、βのキーストーン数、広いツリーUIへの移行目標を記録する。

経済・製造・世界設定・ネットワーク全体の再設計や、既存コードの一括置換は今回の決定対象ではない。

## 2. 決定事項

### D01. 分かりやすい入口と、考えるほど深くなる育成を両立する

職業や基本操作はMMOとして理解しやすくする。AION／Lost Arkのような分かりやすい職業体験を土台にし、PoE的な組み合わせ・投資・経路選択の面白さを取り入れる。

複雑さは、技能数・専用ゲージ・未知の用語を増やすことでは作らない。少数の理解できる行動や効果が、組み合わせによって違う価値を持つようにする。

### D02. 初期βの基本職は5つのプレイスタイルを軸にする

初期βのランダムマップ型の遊びを前提に、次の5職を設計の基準にする。名称未定の職業と、具体的な性能値は残す。

| 基本職 | 合意した大まかなプレイスタイル | まだ固定しないこと |
|---|---|---|
| ウォーリアー | ベーシックで、ある程度硬い近接職。素直に武器を振って戦える。 | 使用武器一覧、技能一覧、HP倍率、ゲージ仕様 |
| タンク系〈正式名称未定〉 | かなり硬い。ランダムマップを自分で攻略できる攻撃能力も持つ。 | 正式名称、盾必須か、具体的な防御・敵制御の方法 |
| メイジ | 非常に脆い遠距離職。魔力／APを主な成長軸とする技能主体の火力。選ぶ技能でダメージの出方が変わる。 | 呪文一覧、属性運用、AP計算、固有ゲージの有無 |
| レンジャー | 弓を使い、継続的な単体ダメージを得意とするマークスマン。 | 射撃操作、技能一覧、集中などの固有資源 |
| アサシン | 脆い近接職。バーストとトリッキーな接近・離脱を軸にする。 | 印・背面・潜伏・分身など、具体的に何を採用するか |

これは標準構成の入口であり、装備やパッシブで耐久・属性・攻撃傾向を変えることまで禁止するものではない。

### D03. 上位職は、基本職ごとにおおむね3系統を長期的に作る

上位職は徐々に追加する方向。初期βで15上位職を揃える約束ではない。基本職だけで楽しく遊べる状態を先に成立させる。

上位職は、基本職の仕組みや既存技能の運用を発展させるものとして考える。「炎職・氷職・雷職」を選ばないとその属性を使えない、といった固定コースにはしない。

具体的な上位職名・効果・解放条件は未確定。3枠を埋めるためだけに追加しない。

### D04. 基本技能は、数合わせではなく実際の遊びの違いで選ぶ

各基本職は、オーソドックスで分かりやすい技能構成を優先する。似た役割の技能や、無理に追加したような技能で候補数を埋めない。

判断基準は「その技能をなくすと、本当に一つの戦い方が失われるか」。通常攻撃で十分に担える小技や、毎回攻撃前に押すだけの強化ボタンは統合・再検討の対象にする。

通常8候補＋奥義2候補、通常4枠＋奥義1枠などの数を、今回の最終仕様として固定しない。意味のある違いが先であり、個数は後から決める。

### D05. 現行WarriorのCD順押しは、確認待ちの仮説ではなくCreatorからの問題報告として扱う

Creatorは「今のままだとなる」と明示した。現行Warriorが、再使用可能になった技能を順番に消化する遊びになっていることを改善対象とする。

今後検証するのは、その問題の有無ではなく、原因と改善策。CD値だけを根拠に原因を断定しない一方、Creatorの実機評価を単なる仮説へ戻さない。

CDを全廃する決定ではない。主力攻撃と、距離・敵の数・危険・攻撃機会に応じて使う技能の区別を作る。主力が全部CD待ちになり、別のボタンで空白を埋める構造を見直す。

### D06. 基本Warriorを、素直な近接戦闘へ戻す

基本Warriorに、精密な受け流しと専用反撃を中心にした操作セットを標準搭載する方向は採らない。現行の受け流し→特定技能の再使用・反撃強化の組を、基本職の完成形として維持しない。

通常攻撃は、技能待ちの埋め草ではなく、自分で敵を倒せる基礎として調整する。ただし全ビルドに通常攻撃の固定回数・固定順序を義務付ける決定ではない。

「近づく・素直に殴る・重く殴る・広く斬る・危険なら回避する」程度の分かりやすい行動を比較基準にする。これはそのまま最終技能リストやスロット数を確定するものではない。

| 現行技能・案 | 今回の設計上の扱い |
|---|---|
| 受け流し／返し刃のセット | 基本Warriorから外す方向。上位職への自動移管やゲーム全体での反撃禁止までは決めない。 |
| 踏み込み斬り／破城突き | 接敵技能としての統合を優先検討。両方必要だとする前提を外す。 |
| 叩きつけ／薙ぎ払い | 素直な重撃・範囲攻撃として残す候補。名称・挙動・付随効果の最終採用は未決。 |
| 牽制斬り／新しい速斬り案 | 通常攻撃との違いが薄ければ統合する。改名して水増ししない。 |
| 雄叫び／不屈の旗 | 基本Warriorの数合わせで維持しない。除外方向で見直すが、他職への移管先は未定。 |
| 天断 | 攻撃奥義の候補として再評価。奥義を必ず2候補用意する決定ではない。 |
| 戦気解放・破砕撃などの新技能案 | 未採用。新技能の居場所を作るために新システムを追加しない。 |

通常の雑魚へ好きな主力を繰り返して気持ちよく勝つことまで否定しない。問題は、ビルドで選んだ主力を使うことではなく、CDが戻った別々の技能を義務的に消化すること。

### D07. ビルドは「戦い方×属性・追加効果」の多様性を持つ

重撃・継続攻撃などの戦い方を選んだ後にも、属性の使い方で違いを作れるようにする。

Creatorが求めた代表的な体験は、重撃に氷を組み合わせて攻撃機会を作る、炎で重撃の間のダメージを補う、雷で重撃の集団処理の弱さを補う、といったもの。

これらは体験の目標であり、凍結時間・燃焼方式・連鎖数・専用の仕込み技能・起爆手順まで確定したものではない。

- 基本技能そのものを、炎斬り・氷斬り・雷斬りのような別技能で数合わせしない。
- 属性で長所を伸ばすだけでなく、好きな戦い方の弱点を補えるようにする。
- 「重撃コース」と「氷コース」を順に完成させる固定制度にはしない。
- すべての属性ビルドに複雑な仕込み順序を要求しない。普段の攻撃で属性を働かせる構成も成立させる。
- 属性なしの素直な能力投資や、キーストーンなしの構成も比較・評価できるようにする。

### D08. 武器は少数の標準適性を入口にし、構成による越境の余地を作る

Creatorの希望と直近レビューで維持した方向は「各職に少数の標準的な適性武器があり、キーストーンなどの条件・交換条件によって、その境界を越える構成も作れる」こと。

ただし、全職×全武器の全組み合わせがβで使用可能になること、どの越境手段を採用するか、正確な装備可能表までは未確定。

武器は、通常攻撃の速さ・一撃・届き方など、操作して分かる差をまず担当する。全武器に専用ゲージ・別ツリー・条件付きパッシブを標準搭載することを前提にしない。

武器系統の数と、モデル・個別アイテムの数は分ける。武器6系統・7系統、Primary／Secondary／Exoticの3段階制度は未確定。

装備できることと、既存技能がその武器で機能することは別なので、越境は対応技能を含む実際に遊べる範囲として設計する。

### D09. 共通パッシブツリーは「必要な能力と組み合わせを取りに行く場所」にする

職業の固定ルートを完成させるためではなく、今の技能・武器・装備に必要な性能や相互作用へ投資する場所にする。

- 各職の開始周辺では、その職業の基本的な戦いに役立つ能力を取れるようにする。
- 欲しい能力へ進む途中に、関係のない能力を無理に強制しない。
- 同じ能力が欲しくても、周囲で何を一緒に得るか・どの経路を通るかを考えられる配置を目指す。
- ノード数や図の複雑さ自体を目標にしない。重なり・追いにくい接続線は、自由度の代わりにはならない。
- Notable〈主要パッシブ〉すべてに新しい条件や挙動を義務付けない。まとまった速度・範囲・HPなど、分かりやすい強化も置いてよい。
- 意味のある挙動変更はツリーにも置く。ただし、通常の遊びを成立させるための必須修理部品ばかりにはしない。
- キーストーンを近くから巡回して集めるだけが強い構造にしない。特定のものを採用しない選択にも意味を持たせる。

### D10. βには15キーストーンを出し、ツリー全体を一通り機能する状態にする

**キーストーン15個は明示決定。最初のβを8個などの縮小版へ置き換えない。** 内部での実装順序を分けることと、βに出す完成範囲を縮めることは別。

Creatorの目的は、未実装の穴による不満と設計そのものの問題を混同せず、実際に構成を作ったプレイヤーからフィードバックを得ること。

「完成」は永久に変更しないという意味ではなく、表示だけでなく効果・到達経路・必要な装備や技能との接続を備え、取得・構成・実戦評価ができる状態を指す。

15個を各職3個へ均等配分する疑似上位職にはしない。採用した戦闘ルールの異なる使い道として設計する。全員に取得を必須にしない。

15個の具体名・効果・配置・併用条件は未決。Small／Notableの総数、ツリーの総ノード数、ポイント上限も未決。

### D11. スキルツリーUIは、狭いインベントリ枠から広いキャンバスへ移す

大きなツリーを見渡し、必要な箇所を拡大・移動して調べられるUIを目指す。最初の移行対象はスキルツリー。

専用クライアントコードの改修を必須としない、サーバー側処理＋リソースパックによる方式を検討対象とする。ただし、動画と同じ操作・描画をMinecraft内で再現できることを検証済みとはしない。

HTML風記法やWeb試作の存在を、任意のHTML/CSSがMinecraftでそのまま動く証明として扱わない。使用ライブラリ、シェーダー、入力取得、パン・ズーム、表示崩れ、フォールバックの具体方式は未決。

会話中のWeb版v1〜v6は操作・設計を試す資料。ノード数・44ポイント・6職起点などを、本番仕様へ自動転記しない。初期基本職の設計基準はD02の5職。

### D12. 未定義の仕組みを、既定の仕様として設計に混ぜない

Stagger〈体勢の蓄積・体勢ゲージ〉は採否保留。武器やツリーの基準値として採用済み扱いしない。

被弾の演出、敵の行動中断、一定時間の行動不能、防御低下、体勢の蓄積は別の仕組みとして区別する。関連する名前のコードが存在しても、共通の体勢システムが承認されたことにはならない。

同様に、全職の固有ゲージ、全武器の特殊パッシブ、特定の凍結・連鎖・資源変換ルールも、必要性と採否を決めてから仕様にする。

## 3. 接続条件

技能・武器・属性・パッシブ・上位職は相互に作用するが、同じ役割を無計画に重複させない。技能の基礎挙動、武器の手触り、属性の働き、数値投資、ルール変更の担当を詳細設計で明示する。

設計変更は、既存データの削除や初期化を伴うものとして自動採用しない。旧構成の返還・移行・武器適性変更時の扱いは未決台帳で決める。

実装済み、ビルド成功、自動テスト成功、レビュー済み、実機の手触り合格、β投入可能は別の状態として記録する。

## 4. 確認用の仮定・例示の扱い

次は比較のための案であり、採用済みではない。

- Warriorの比較用編成：通常攻撃＋接敵＋重撃＋範囲攻撃＋回避。
- 属性差の比較例：同じ重撃に氷・炎・雷を組み合わせる。
- キーストーン例：不凍の核、雷霆収束、残火起爆、元素闘気、戦闘魔術など。名称も効果も未確定。
- 武器候補：大剣、片手武器、槌、弓、短剣、杖、盾など。独立系統として採用する数は未確定。
- ツリー案の各ノード数、Notable50〜70、総ノード250〜350、Web版44ポイントなどの過去の数値。

## 5. 今回決めないこと

技能一覧と入力枠、各技能の係数・範囲・時間・CD、マナと固有資源の役割、武器系統と適性表、属性の内部ルール、15キーストーンの個別仕様、Notableの数と内容、ツリー配置とポイント成長、取得・返還・保存、上位職の詳細、UI実装方式、敵の制御耐性、β開始日時と計測手法。

これらは[未決事項の台帳](2026-09-19-combat-build-open-questions.md)で、今回の合意と混ぜずに扱う。
