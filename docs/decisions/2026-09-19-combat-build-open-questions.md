# ProjectS — 決めるべきことと未採用案

> 本書の質問・検証案・優先順は、未決事項を整理したもの。選択肢や推奨手順が書かれていても、それを採用済み仕様として実装しない。

記録日：2026年9月19日。

正本となる合意記録：[戦闘・職業・ビルドの決定記録](2026-09-19-combat-build-direction.md)

## 1. 決まっていることを、再び未決へ戻さない

- βは15キーストーンを備えたツリーを一通り完成させて出す。8個などへの縮小は未決の選択肢ではない。
- 基本職の入口はオーソドックスで分かりやすくする。基本Warriorの受け流し・専用反撃セットを、そのまま標準の中核として維持しない。
- Creatorが報告した現行WarriorのCD順押しは改善対象。問題の有無を再確認することを、修正検討の前提にしない。
- 技能、武器、Notableを先に個数へ合わせて水増ししない。
- 戦い方と属性などの組み合わせによる多様性、能力・経路を選んで育てるツリーを目指す。
- Staggerを共通の体勢ゲージとして採用したとは扱わない。

## 2. 決める順序の提案

次は依存関係を踏まえた進め方の提案であり、新しいリリース条件や締切ではない。

1. Q01〜Q03：Warriorで何を入力し、何を主力にし、何を消費するか。
2. Q04〜Q06：武器と適性・越境、属性、他4職の基本構成を並行して定義する。
3. Q07〜Q09：上で定義したルールに基づき、15キーストーン・Notable・ツリーを設計する。
4. Q10〜Q13：返還・保存・UI・敵との相互作用を接続する。入力と表示の技術検証は早期に並行してよい。
5. Q14〜Q15：β全体の合格条件、フィードバック手法と投入版を固定する。

重要なのは、先に15個の名前や数百ノードを埋めてから、それを成立させるための戦闘ルールを追加しないこと。内部の比較試験を小さく区切っても、βに出す完成範囲は縮小しない。

## 3. 未決事項一覧

### Q01. 戦闘の基本操作と技能枠

**決めること**
- 通常攻撃、選択技能、奥義、回避／防御を何に割り当てるか。
- 通常攻撃はクリック、長押し、その他のどれを使うか。ブラウザではなくMinecraftの対象環境で成立する入力を確認する。
- 装備できる技能枠数、奥義の有無と枠数。現在の4＋1を維持するかも含めて決める。
- 技能候補の選択権、同時に持ち込む数、入れ替え可能な場面を分けて決める。
- 技能をレベルで段階解放するか、基本技能を最初から／短い導入後に選べるようにするか。
- 非戦闘時の変更、戦闘中の固定、入れ替え時のCDや資源の扱い。

**Creatorの希望として保持すること**
「いつでも好きなスキルを使えてもいい」という、早期の選択自由への希望がある。ただし、全技能Lv1解放、4＋1固定、戦闘中の自由な入れ替えまで確定したとはしない。

**決定の出口**：基本操作表、技能選択・解放・入れ替えのルール。

### Q02. Warriorの最終的な基本技能構成

**決めること**
- 普段の主力は何か。通常攻撃がどこまで敵を倒す役割を持つか。
- 接敵、重撃、範囲攻撃、自己防衛、奥義として、どの行動を採用するか。
- 踏み込み斬りと破城突きの統合、牽制斬りと通常攻撃の役割整理。
- 叩きつけ、薙ぎ払い、天断を残すか。残す場合、何を外して何を調整するか。
- 基本職から外す受け流し・返し刃、見直し対象の雄叫び・不屈の旗の扱い。将来候補として保持するかも未決。
- 各技能の発生・攻撃後の隙・射程・範囲・単体／集団効率・移動中の使用・攻撃中断の条件。
- 通常攻撃と比較して、その技能を押す理由が本当にあるか。

**決めないまま実装しないこと**
速斬り、戦気解放、破砕撃などを、新8技能の空欄埋めとして追加しない。技能の説明が違うだけでは、別技能が必要だと判定しない。

**決定の出口**：採用技能だけの一覧と、各技能の用途・制約・通常攻撃との差。

### Q03. CD・マナ・固有資源の分担

**決めること**
- Warriorの闘気を残すか。残すなら何で増え、何に使うのか。
- 普段の攻撃や基本技能を使うために、どの資源・CDが必要なのか。
- 主力攻撃の頻度を制限する仕組みと、接敵・防御・奥義の再使用制限を分けるか。
- 全職に固有ゲージを持たせる必要があるか。採用する職業ごとに判断する。
- 攻撃速度・詠唱速度・再使用短縮が、発生・攻撃後の隙・回数へどう作用するか。
- 資源変換が入った場合の上限や、再帰的な獲得の防止。

**禁止する早合点**
「CDを全部なくす」「全職にマナと固有資源を必ず両方付ける」「通常攻撃を一定回数挟ませる」は未決。

**決定の出口**：各職の資源図と、代表的な戦闘での行動・資源収支。

### Q04. 武器系統・標準適性・越境

**決めること**
- βで独立した武器系統を何種類作るか。大剣、片手剣、槌、短剣、弓、杖などのどれを採用するか。
- 盾、二刀、杖／魔導具などの主手・副手の構成。
- 通常攻撃、攻撃範囲、動作、性能、技能への影響のどこで差を出すか。
- 5職それぞれの標準適性表。適性がない武器を装備できないのか、装備はできるが特定技能が使えないのか。
- βで対応させる越境の範囲。Creatorの「全部使える余地がほしい」という希望を、どの段階・どの条件で実現するか。
- 越境で変えるのは装備許可、通常攻撃、技能の使用条件、係数、挙動のどこか。
- 弓で近接技能を使う等、別の描画・判定が必要な組み合わせをどう扱うか。
- 武器の見た目違いとゲーム上の独立系統を区別する。

**決定の出口**：武器系統表、職業×武器の適性表、越境ごとの対応技能と交換条件。

### Q05. 属性・状態異常の基礎ルール

**決めること**
- βで扱う属性。氷・炎・雷を中心にした案から、実際の採用範囲を確定する。
- ダメージ属性、状態異常、状態異常を利用する追加効果を区別する。
- 冷却・減速・凍結、燃焼、帯電・放電・連鎖がそれぞれ何を意味するか。
- 一撃の強さ、命中回数、継続ダメージが、属性の発生や蓄積へどう作用するか。
- 武器の攻撃力／魔力／AP、物理・属性ダメージの計算と表示。
- 技能・装備・MOD・パッシブのどこから属性を得るか。初歩的な属性をいつ試せるか。
- 複数属性、純物理、技能ごとの属性変更をどう扱うか。
- 雑魚・精鋭・ボスでの状態異常、行動停止への耐性。
- 他人の攻撃が自分の仕込みを消費するか。共有する状態と個人の効果を区別するか。
- 追加攻撃が別の追加効果を起こせる範囲、無限連鎖の防止。

**未採用の例**
残り燃焼の起爆、凍結を脆化へ変える、連鎖回数を単体威力へ変える等は、基礎ルールが決まる前に既定機能として扱わない。

**決定の出口**：属性ごとに、付与→状態→利用→終了を説明できる仕様。

### Q06. 他4職の基本技能と、5職共通の最低限の機能

**決めること**
- タンク系の正式名称と、盾・防御・敵の位置操作・自身の火力の内訳。
- メイジの初期呪文と自衛手段。三属性の順番管理や第二資源を必須にするかは未決。
- レンジャーの射撃操作と、単体・集団への対応。
- アサシンで採るトリッキーな仕組み。印、潜伏、背面、分身を全部載せる前提にしない。
- 各職の回復、戦闘間の立て直し、ソロ／パーティの成立。
- 現行のHealer／Starweaver等をβでどう見せるか。今回の5職案を理由に保存やコードを自動削除しない。

**決定の出口**：各職の最小の戦闘説明、採用技能、ソロでの対処と協力時の価値。

### Q07. βの15キーストーンの個別仕様

**決めること**
- 15個すべての名称、変えるルール、得るもの、失うもの。
- 対応する職業・技能・武器・属性。使い道のないノードがないか。
- 前提条件、配置と必要ポイント、併用可能／排他の組み合わせ。
- 「挙動が変わる」と「大きい数値を得る」の区別。
- 固有資源を変えるキーストーンを、職業限定にするか共通化するか。
- 運用上の上限と、矛盾するルール変更の優先順位。
- 関連する技能・武器・状態異常が実装され、実戦で試せること。

**固定済み**：β投入数は15。5職×3固定配分ではない。

**未確定**：会話中の15個の内訳、最初の8個案、個々の名称・効果。1人が取得できるキーストーン数の上限も未決。

**決定の出口**：15行の採用表と、各項目の成立例・非適合例・相互作用テスト。

### Q08. Small・Notableの内容と数

**決めること**
- 用意する基礎ステータスの一覧と分かりやすい表示名。
- 数値強化Notableと、相互作用を増やすNotableの役割配分。
- 重撃、直接命中などの共通分類を使うなら、その定義と技能画面での表示。
- 同じ挙動を、技能改造・装備・パッシブのどこへ置くか。
- 各クラスタの目的、周囲の小ノードの内容と効率。
- 総数と、同じ能力を別地域に配置する方針の具体化。

**未確定**：総ノード250〜350、Notable50〜70等の過去の数字。Notableを全部挙動変更にする案は採用しない。

**決定の出口**：能力辞書、クラスタ一覧、ノード採用表。

### Q09. ツリーの地形・開始位置・ポイント成長

**決めること**
- 5基本職の開始位置と、隣の領域へ移る経路。
- 開始直後の数ポイントで、何を得てどんな違いを体験するか。
- 取得可能なポイント総数と、レベル等による獲得速度。
- 移動用ノードの能力。固定補正と選択補正をどこで使うか。
- 主要ノードへの複数経路、地理的な傾向、無意味な取得の強制をどう避けるか。
- 前提条件・接続の判定、ルール変更ノードを迂回できる経路。
- ツリー全体の可視性と、初心者に最初に見せる範囲・案内。

**注意**：Web版v6の664ノード・44ポイント・6職起点は確定値ではない。過去の試作をそのまま採用しない。

**決定の出口**：5起点を持つノードグラフ、ポイント成長表、序盤と終盤の経路検証。

### Q10. 取得・返還・構成保存・既存データ移行

**決めること**
- ノードの選択と取得確定を分けるか、経路のまとめ取得を提供するか。
- 返還時に孤立する後続ノードを禁止するか、一緒に返還するか。
- 振り直しの条件・場所・費用、βの試行錯誤を妨げない範囲。
- 構成保存、比較、書出し・読込の必要範囲。
- 職業変更・武器適性変更・技能削除時に構成をどう復旧するか。
- 旧ツリーからのポイント返還・ノードID・版管理・バックアップ。
- 二重取得、古い画面からの操作、保存失敗などの扱い。

**注意**：自由な振り直しや保存枠数は有力な検討項目だが、具体制度は未確定。

**決定の出口**：操作・保存・移行仕様。プレイヤーデータを無断で初期化しない手順。

### Q11. 新しい大画面ツリーUIの実装方式

**決めること**
- サーバー側＋リソースパック方式で使う描画・入力手段、外部ライブラリの可否とライセンス。
- 実際のMinecraft環境でのクリック、カーソル、パン・ズーム、ホバー、閉じる操作。
- カメラ・移動・攻撃入力をどう扱い、閉じたときや切断時に何を復旧するか。
- GUIスケール・解像度・FOV・対象クライアント構成での検証範囲。
- リソースパック拒否・読み込み失敗・互換性問題のフォールバック。
- 検索、経路比較、現在の技能へ何が作用するかの表示。
- 画面外の表示省略、通信量、表示オブジェクト数などの負荷対策。

**注意**：Webでマウス操作できることは、Minecraftでも同じ入力が取れる証拠ではない。HTML/CSS全互換や動画方式の採用・移植完了は宣言しない。

**決定の出口**：一画面での実機技術検証と、その後のツリー全体への接続条件。

### Q12. 敵・ランダムマップ・協力戦闘との接続

**決めること**
- 5職が基本構成で対処できる敵・地形の範囲。
- 範囲攻撃、単体攻撃、射程、移動が役立つ遭遇の配分。
- 予兆、攻撃機会、接近・離脱する空間をどう作るか。
- タンクが硬いだけで全ての場面に最適にならない差、脆い職が事故死だけで終わらない対処。
- 状態異常、行動中断、ボスの攻撃機会とパーティ人数の関係。

**決定の出口**：共通の比較用遭遇、職業・構成別の得意不得意、対処できない配置の禁止条件。

### Q13. Staggerなど追加システムの採否

**決めること**
- 共通の体勢蓄積や体勢ゲージを必要とするか。採用しない案も含む。
- 既存の一時的なボス行動停止やギミック後の攻撃機会を、新仕様でどう扱うか。
- 重い攻撃の価値を、一撃・届き方・属性だけで作れるか。

**固定する注意**：ゲージ表示を隠すだけでは、仕組み自体が単純になるとは限らない。採否を決めるまでは、体勢ダメージや体勢ノードをβの仕様へ混ぜない。

**決定の出口**：必要な遊び、採否、採用する場合の用語とルール。

### Q14. βの完成条件とフィードバック

**決めること**
- 15キーストーンとツリー全体について、実装・自動テスト・レビュー・実機確認をどう判定するか。
- 比較する装備水準、使用ポイント、敵・マップ、ソロ／パーティの条件。
- 攻略時間、倒れる頻度、回復消費、実際に攻撃できる時間、構成の違いなど、何を測るか。
- 初心者の理解、技能を使う理由、属性変更後の欲しい能力をどう聞くか。
- ノード取得・返還・組み合わせ・職業武器分布など、行動データを収集するか。
- 収集する場合の識別子、目的説明、保存期間、同意・プライバシー対応。匿名収集をすでに実装したと扱わない。
- 人気があることと強すぎること、取得が少ないことと未到達・未発見をどう区別するか。

**固定済み**：完成した評価対象をβに出して、実際のプレイヤーフィードバックを得たい。

**決定の出口**：β合格チェックリスト、質問票、採用する計測仕様。

### Q15. β投入版と将来拡張の境界

**決めること**
- βの基準ブランチ・コミット、配布物、パックの組み合わせ。
- 実装計画、レビュー、既存データへの適用とロールバック。
- β開始日・対象者・参加人数・実施期間。今回の会話だけで新しい日程は設定しない。
- 上位職を追加する順番と、基本職の体験を壊さずに加える条件。

**固定済み**：上位職を各職3系統程度へ徐々に広げる方向。βで15上位職を実装する決定ではない。

**決定の出口**：βリリース契約と、今回含めない内容の一覧。

## 5. 以後の記録方法

一つの未決項目を確定するときは、決定内容、理由、今回含めないもの、技能・武器・属性・保存・UIへの接続条件を記録する。確認用の仮定は仮定のまま残す。

確定後は合意記録へ追記し、本台帳の該当項目を解決済みにする。コードが書かれた、Web画面に置かれた、他作品に似た例がある、という理由だけで解決済みにしない。
