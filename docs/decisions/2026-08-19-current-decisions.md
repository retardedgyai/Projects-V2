# ProjectS v2 現在の決定事項

最終更新: 2026-08-19

この文書は、ProjectS v2 のリライト開始前に確定・仮決定した内容を一か所に集めた現在の基準書です。

表記:
- **決定**: 当面この前提で実装する。
- **仮決定**: 最初の試作で検証し、触った結果で変えてよい。
- **後回し**: 方向性はあるが、初期実装には入れない。

## 1. プロジェクト全体

- **決定**: ProjectS v2 は旧 ProjectS の完全リライトとして扱う。
- **決定**: 旧コードは資料・歴史・失敗例・テスト観点として残すが、新コードへそのまま移植しない。
- **決定**: 新しい正式リポジトリは `Projects-V2`。
- **決定**: Kotlin-first。Java は Fabric/Mixin など境界で明確に安全な場合だけ許容する。
- **決定**: Gradle Kotlin DSL を使う。MavenではなくGradleを使う主理由は、Fabric Loomを含めサーバー/クライアントを同じビルド基盤へ揃えるため。
- **決定**: モノレポで server / client / protocol / domain / content / mob-editor / tests を管理する方向だが、初日に空モジュールを大量作成しない。

## 2. ゲームの初期構造

- **決定**: 初期版は巨大オープンワールドではなく、港町を共有拠点にした討伐型オンラインAction MMO。
- **決定**: 基本ループは `港町 → クエスト選択 → 1〜4人専用討伐空間 → ボス → 個人報酬/素材 → 装備更新 → 次の討伐`。
- **決定**: 個人Lootを基本とする。
- **決定**: 最初の完成単位は `港町の一部 → 1クエスト → 1マップ → 1ボス → 1素材 → 1装備更新 → 再挑戦`。
- **後回し**: オープンワールド、複数都市、マーケット、ギルド戦、大規模経済、専用Launcher。
- **決定**: 最初からBeta全体を作らず、実際の一連の遊びを最小構成で完成させてから横へ広げる。

## 3. Editor / 制作ツール

- **決定**: 人間向けEditorとして残すのは Mob Editor のみ。
- **決定**: Skill Editor / VFX Editor / ProjectS Studio / VFX World Builder / Balance Editor / 汎用ノード・タイムラインEditorは作らない。
- **決定**: 視覚エフェクトはコード/データ/AIで制作し、必要ならデバッグ表示と即時反映を整える。
- **決定**: 「ゲームより制作基盤を先に作る」状態へ戻らない。

## 4. 開発環境

- **決定**: Minecraft Java Edition 26.2 をリライト開始時の基準バージョンに固定する。
- **決定**: Java 25。
- **決定**: Server は Minestom 26.2 系を第一候補として開始する。
- **決定**: Client は Fabric 26.2 を内部基盤として使う専用 ProjectS Client。
- **決定**: Snapshot / Pre-release は追わない。Minecraftの新安定版が出ても即更新せず、更新用Branchで検証してから上げる。
- **決定**: Minecraft 26.2の現行描画方式に合わせ、生OpenGL依存のVFX基盤は作らない。
- **決定**: IntelliJ IDEA をコード閲覧/デバッグ/Gradleの主IDE候補とし、Codex/OpenCode等をAI実装に使う。
- **目標**: `./gradlew runServer` / `./gradlew runClient`、可能なら一発で開発環境を起動できるタスクを用意する。

## 5. Server / Client の責務

- **決定**: 最終判定はServer側。Damage、Hit、Reward、ProgressionをClientに信用させない。
- **決定**: Clientは入力直後に見た目・音・カメラ反応を出して操作遅延を感じにくくする。
- **決定**: ServerのゲームルールとClientの見せ方を分離する。
- **決定**: 統合版対応は初期から考えない。Java専用Clientの強みを優先する。
- **後回し**: 成功後に必要ならProjectS専用Minestom Forkやより深いClient独自化を検討する。現時点でMinestomをForkしない。

## 6. 討伐空間

- **決定**: 1回のクエストを `HuntSession` 的な一時実行単位として扱う。
- **決定**: `作成 → Map読込 → Party投入 → Mob/Boss/Combat開始 → 報酬確定 → 港町へ戻す → Mob/判定/Timer/Eventを掃除 → Instance破棄` まで寿命を明確にする。
- **決定**: 討伐中のHP、Boss状態、空間そのものは一時状態。
- **決定**: 装備、素材、進行度などは永続状態。
- **決定**: 初期は1プロセスでよい。Redis/大量のMicroservice/Orchestratorは作らない。
- **後回し**: 人数が増えたらHub/Hunt/Party等を役割ごとに分離できる構造へ発展させる。

## 7. 戦闘視点と基本操作

- **決定**: 一人称を正式な戦闘基準にする。Minecraft特有の没入感を優先する。
- **決定**: 三人称を使いたい人は使えてよいが、戦闘/VFX/Boss予兆は一人称基準で調整する。
- **決定**: ロックオンなし。自動で敵方向を向かない。攻撃は照準方向へ出す。
- **決定**: Skill 1 / Skill 2 / Skill 3 / Ult 1つから開始する。単調なら後から増やす。

## 8. 通常攻撃

- **決定**: Minecraft Vanillaの近接通常攻撃を全武器の共通仕様にはしない。
- **決定**: 「通常攻撃 = その武器の一番基本的な戦闘動作」と定義する。
- **仮決定**: 近接通常攻撃は長押しで継続する。高速Attack Speedでも高速クリックを要求しない。
- **決定**: Clientは通常攻撃の `押した / 離した` という状態変化だけをServerへ送り、保持中を毎tick送らない。Serverが保持状態と攻撃テンポを管理する。
- **決定**: 一撃は最低限 `攻撃が出るまで / 攻撃判定中 / 攻撃後の隙` の3段階で扱う。
- **決定**: 「一撃終了」は攻撃後の隙まで完了した時点。
- **決定**: 通常攻撃中にSkillまたは回避を押しても現在の一撃を途中キャンセルせず、一撃終了後に実行する。
- **決定**: Attack Speedはクリック要求ではなく武器そのもののテンポを変える。
- **決定**: 武器ごとにAttack Speedの効き方を変えてよい。大剣は重さを残して主に攻撃後の隙/次行動への移行へ効かせ、穿龍棍系は一撃全体のテンポへ比較的強く効かせる。
- **決定**: 弓の「右クリック長押しで引いて、離して撃つ」などVanillaで既に気持ちいい挙動は無理に捨てない。
- **決定**: 通常攻撃そのものに複雑な派生を必須にしない。必要な武器だけ追加する。

## 9. 攻撃判定

- **決定**: Vanilla melee hitを主判定にせず、ProjectS独自の空間攻撃判定を使う。
- **決定**: 武器/攻撃ごとに、扇、細い突き、近接打撃、円形衝撃、突進範囲、Projectile等を定義する。
- **決定**: 視覚エフェクトとServer側判定の形は可能な限り一致させる。
- **決定**: 1回の攻撃で同じ対象へ意図せず複数回Hitしない。多段技は多段Hitを明示的に定義する。
- **決定**: 一撃ごとにServer側の一意な実行IDを持たせ、命中通知をその実行と関連付ける方向でDay 1を作る。
- **後回し**: 必要なら前回位置→今回位置の軌跡まで判定する高精度なSweepへ発展させる。

## 10. Mob / Bossの攻撃

- **決定**: PlayerとMobは同じ「明示的な攻撃判定」という戦闘文法を使う。
- **決定**: Mobに近づいた/触れたこと自体では原則Damageを受けない。
- **決定**: 爪、牙、拳、角、尻尾、突進、魔法などもMobの攻撃手段として明示的に定義する。
- **決定**: 大型Mobの身体衝突とDamage判定は別。身体にはめり込めないが、触れただけでDamageにはしない。
- **決定**: 炎オーラ等の接近危険も「明示された危険領域」として定義する。
- **目標**: 上手い近接PlayerはBossの至近距離で攻撃判定だけを最小移動で避け、攻撃継続時間を最大化できる。

## 11. 回避

- **仮決定**: `WASDの現在入力 + 回避キー` でその方向へステップする。
- **仮決定**: 8方向対応。
- **仮決定**: 距離は約3ブロック。開発時に2.0 / 2.5 / 3.0等を即比較できるようにする。
- **仮決定**: 初期試作では無敵時間なし。
- **仮決定**: 初期試作ではスタミナなし。
- **仮決定**: ステップ中の再ステップ不可。
- **仮決定**: 地上のみ、壁に当たったら停止、視点自由。
- **決定**: 攻撃中に回避を押した場合、現在の一撃を途中キャンセルせず、一撃終了後に回避する。
- **決定**: 武器ごとの途中キャンセル時間は最初から作らない。実際に遊んで必要になった場合だけ追加する。

## 12. 通信遅延

- **決定**: 初期は複雑な時間巻き戻し判定を作らない。
- **決定**: Serverの現在状態でHit/回避を判定する。高Pingで多少不利になることは許容する。
- **決定**: その代わりClientの入力/見た目反応は即時にし、Boss攻撃自体も読みやすい設計にする。
- **後回し**: 実テストで100〜150ms程度でも理不尽な被弾が頻発する場合にのみ軽い補正を検討する。

## 13. 被弾の重さ

- **決定**: Server/World全体を止める本物のHit Stopは使わない。
- **決定**: 命中時の重さはClientだけの火花、Impact Sound、小さいCamera反応、Damage Number、短い視覚強調で作る。
- **決定**: 空振りと命中の感覚を明確に分ける。

## 14. 視覚エフェクト

- **決定**: 攻撃Animationがなくても、斬撃軌跡そのものを攻撃表現として成立させる。
- **決定**: 大量の粒子より「形が読める」ことを優先する。
- **参考方針**: Minecraft Dungeonsのように、弧=斬撃、線=突き/Beam、Ring=衝撃波など視覚言語を統一する。
- **決定**: Human-facing VFX Editorは作らない。
- **決定**: Combat Spikeでは高品質Rendererや汎用VFX基盤を作らず、既存Particle/単純な線や弧/Soundで検証を優先する。

## 15. マナ / クールダウン / 固有ゲージ

- **決定**: 全Playerに「マナ」という共通概念を持たせる。
- **決定**: Skill 1〜3は原則としてマナを消費する。
- **決定**: 通常攻撃と回避はマナを消費しない。
- **決定**: 戦闘中もマナは自然回復する。
- **決定**: 戦闘外ではマナをより高速に回復する。
- **決定**: クラス、Skill、装備、MOD等が追加のマナ回復方法を持ってよい。
- **仮決定**: Ultは通常Skillと同じマナだけで制限せず、Ult固有条件/ゲージ等を後で検討する。
- **決定**: クラスごとに「マナをどれだけ意識させるか」を大きく変えてよい。
- **決定**: マナ管理を主役にしたくない戦士等は、普通に使う限りほぼ枯れない程度に消費を軽くする。
- **決定**: Mage等はマナ消費を重くし、最大マナ/回復/消費軽減をビルドとして考えさせてよい。
- **決定**: 一部Mageは、個別Cooldownを極端に短く/ほぼ無しにして「マナさえあればスキルを連打できる」設計も許容する。
- **決定**: マナ関連MODは全クラス共通で存在できるが、価値はクラス/ビルドによって大きく違ってよい。
- **決定**: 固有ゲージはマナの二重課税ではなく、「そのクラスらしく上手く戦った報酬」として使う。
- **決定**: 固有ゲージの「どう溜めるか」はクラスのアイデンティとして固定し、「何へ変換するか/どう使うか」はビルドで変化させられる方向を採用する。
- **決定**: ただし最初から固有ゲージ汎用システムを作らない。最初は一つのクラスで、一つの溜め方 + 一つの使い道だけ実装して遊ぶ。別クラスが必要になった時にその実例から広げる。

## 16. クラス / 武器 / Skillの責任分担

- **決定**: 武器は通常攻撃、射程、攻撃範囲、基本テンポ、一撃の重さなど「基本攻撃の遊び」を担当する。
- **決定**: クラスは Skill 1〜3 / Ult、マナの扱い、固有ゲージ、戦闘上の基本性格を担当する。
- **決定**: Skill 1〜3はクラス由来を基本とする。
- **仮決定**: クラスごとに使用可能武器を限定する。
- **仮決定**: 最初の3クラス×3武器案は次の通り。
  - 戦士系: 片手剣 / 大剣 / 槍。
  - 遊撃系: 穿龍棍系 / 双剣 / 弓。
  - 魔術系: 杖 / 魔導書 / 魔導具。
- **注意**: クラス名、武器名、9武器すべての正式採用はまだ固定しない。最初の実装はHeavy BladeとTwin Rods等の少数だけでよい。

## 17. マナから広げられるビルド例

正式仕様ではなく、可能性として残す。

- 最大マナを盛って短時間に大量のSkillを吐く。
- マナ回復を盛って長時間Skillを回し続ける。
- 消費軽減を積む。
- 命中時にマナを取り戻す。
- 大量のマナを消費するほど次の攻撃を強化する。
- 現在マナが多いほど強い。
- 逆にマナを使い切ることで覚醒する。
- マナ消費を増やす代わりにSkill威力を上げるMOD。
- 味方へマナを供給するSupport。

## 18. Mob / Bossの見た目

- **決定**: 初期の通常Mob/BossはVanilla EntityやPlayer型NPC+Skinを基本にしてよい。
- **決定**: 独自大型Bossモデルはゲーム成立の必須条件にしない。
- **研究継続**: Meshy / Tripo / Sloyd等のAI 3D生成で、Blockbenchや手作業AnimationなしにMinecraft向け大型Mobを作れるか検証する価値がある。
- **研究方針**: ピクセル/低ポリ/角張った形+低解像度TextureをProjectSのCreature Style候補とする。
- **研究方針**: GLB/FBXをMinecraft標準Mob形式へ無理に変換するのではなく、Fabric Clientで骨付きMeshを描画し、必要ならBuild時にProjectS専用軽量形式へ変換する。
- **研究方針**: Clientは3D形状/Texture/Skeleton/Animationを持ち、Serverは必要な骨位置/身体判定/攻撃判定だけを持つ。
- **研究方針**: 騎士+馬+武器のような複合Bossは、1モデルで生成せず部品を別生成して骨へ接続する方針を優先する。
- **研究方針**: 恐竜型等の長い尻尾攻撃は、尻尾骨に沿った単純な判定をServer側で動かす。
- **未決定**: AI 3Dを正式なMob制作手段にするかは技術試験後に決める。

## 19. 初日のCombat Spike

- **決定**: 最初の開発日はproduction combatを完成させる日ではなく「戦闘が面白いか」を判定する実験日。
- **決定**: 試験武器は重い剣と穿龍棍系。
- **決定**: 攻撃速度はまずBaseline / +50% / +100%程度を切り替えて比較する。Server tickより細かすぎる極端値は初回試験で使わない。
- **決定**: 長押し通常攻撃が楽しいか、高速Attack Speedが入力連打ではなく武器のFantasyを強化するかを見る。
- **決定**: 攻撃速度/武器/回避距離などは、EditorやHot Reload基盤ではなく最小の開発コマンド等で再コンパイルせず切り替えられるようにする。
- **決定**: Dummyに加え、可能なら明示的攻撃を2種類だけ持つ簡単な敵を用意する。
- **決定**: 接触Damageなし、攻撃判定を本当にステップで避けられるか試す。
- **決定**: 面白くなければ数日磨き続けず、方式を捨ててやり直す。

## 20. 旧Ability Runtimeから持ち越す考え方

- **決定**: 旧Ability RuntimeのJava/Bukkit実装はそのまま移植しない。
- **保持する思想**: Player/Mob/Bossで共有可能な能力実行、開始/完了/中断/失敗、予約処理の掃除、発動元/対象の明示、Server最終判定。
- **決定**: v2で最初から完成版Ability RuntimeやAction Registryを作らない。
- **決定**: 実SkillやMob攻撃を2〜3個作り、実際に重複した寿命管理/予約/中断だけを小さく抽出する。

## 21. 将来の大規模MMO / GvG

初期Scopeではないが、方向性として保存する。

- **将来方針**: ProjectS v2成功後、港町+討伐から完全オープンワールドMMOへ拡張する可能性がある。
- **将来方針**: ServerはFabric Dedicated Serverへ自動的に移行するのではなく、Minestomを拡張し、必要ならProjectS専用Fork/専用Server Platformへ進化させる。
- **将来方針**: 300vs300級のGvGを将来目標として狙う価値がある。ただし近傍検索、軽量Projectile、表示/通信の距離別簡略化、VFX Budget等の大規模戦専用設計が必要。
- **将来方針**: GvGはAlbion Onlineのような `仕掛ける → 敵をまとめる → 範囲火力を重ねる → 離脱` の集団戦を強い参考にする。
- **将来方針**: 敵が密集して範囲攻撃へ大量に巻き込まれた場合、それを保護するのではなく「大量Hitを成功させた側」を評価する。
- **将来候補**: AlbionのAoE Escalationのように、一度に多数へ当てるほど範囲攻撃の威力が上がる仕組み。
- **注意**: CC時間まで人数に応じて強化しない。大量Hitの報酬は主にDamage等へ置き、長時間操作不能の連鎖は避ける。

## 22. まだ決めていない主な項目

- 通常攻撃終了時にSkillと回避が両方予約されていた場合の優先順位/先行入力詳細。
- 各武器でAttack Speedを3段階のどこへ何%効かせるかという最終式。
- Skill 1〜3それぞれの具体内容。
- Ultの獲得/消費方式。
- 各クラス固有ゲージの具体的な溜め方/効果。最初の1クラス以外は必要になってから決める。
- 被弾時の怯み/吹き飛び/よろめき。
- Boss攻撃の予兆をどこまで身体動作/VFX/床表示で見せるか。
- 討伐中の死亡/復活/味方蘇生ルール。
- 3クラス9武器案の正式名称/最終採用。
- 装備Slot、強化段階、MOD個数、成長システムの詳細。
- 最終的なPersistence製品/DB。
- AI 3D Boss pipelineの正式採用。

## 23. 最優先原則

1. ゲームよりFrameworkを先に作らない。
2. まず実際に触れる一つの機能を作り、必要になった共通部分だけ抽出する。
3. 一人称のMinecraftらしい没入感を捨てない。
4. 装備や数値だけでなく、Player自身が攻撃を狙い、敵の攻撃判定を避ける余地を残す。
5. AI/Editor/基盤の完成より、実際のゲームループが面白いことを優先する。
6. 試作品が面白くなければ、過去の作業量を理由に残さない。
